Failures

Two failures, two remedies

One is our own budget pushing back (wait — and stop refreshing), the other is the door (sign in again). Different causes, different actions, so they must never look like one generic “error”.

D19 ⚠Airtable rate limit — the bot has priority

Data paused for 30 seconds

The booking assistant and this dashboard share one Airtable base (5 requests per second, base-wide). The limit was just hit, so the dashboard steps back and lets the bot through — customers keep getting answers; you get your data a moment later.

Please don't keep pressing refresh — every extra attempt extends the penalty for the bot too. The button re-enables itself.

re-enabling in 24 s

Showing the last successful read — 15:22. Times and statuses may have changed since.

This is Risk 2 made visible. The message is not “slow” or “try again”: it names the shared budget, says the bot wins, and disables the one control that would make things worse. The stale-data line keeps the numbers honest while they are frozen.

D16 🕳Recent errors — no source

Not available in this version

A list of recent system errors would have to come from the workflow engine's execution log, and that log can't be read from here. Rather than show an empty list that looks like “no errors”, this panel stays honestly blank.

What you can rely on: every incident that touches a conversation appears in the handoff queue with its alert class, and the owner alerts go to Telegram.

§4.d marks D16 as “KAYNAK YOK”. An empty list here would be the exact lie this project forbids — “no recent errors” when the truth is “we cannot see them”. The gap is drawn, labelled, and pointed at what does work.

source D16 · §4.ddata source none — n8n log not externally queryable

Switch warning

When alerts are off.

§4.d: ownerAlert.enabled=false silences every alert class, and there is no second channel. If the dashboard rendered that as a normal “off” toggle, the owner would read a silent system as a calm one — so it takes over the panel.

Owner alerts are switched OFF

While ownerAlert.enabled = false, no alert of any class reaches Telegram — handoffs, calendar mismatches, spend caps, background-job failures: all silent. There is no second channel. A quiet queue means nothing until this is back on.

Rendered as a full-width oxide block, not a chip: this is the one switch whose “off” state can hide every other problem on the page.

24 alert classes

Grouped by what the owner has to DO about them — and styled by the same class families the widget uses, so a fault always looks like a fault.

Specimen

Every badge, by what it demands

Source: Build Owner Alert (main, 21 static classes across 28 source nodes) + dynamic zernio_send_failed + the reminders and purge workflows' own alert builders — 24 classes (SCREEN-INVENTORY §4.c). Badge families follow the locked widget contract: solid muted = conversation · dashed oxide = external system down · oxide-soft = budget guard · filled oxide = calendar/Airtable mismatch (the urgent group) · heavy oxide outline = the customer never got a reply.

Conversation handed over 3 classes → take the conversation, then release the lock (D11)
handoff handoff_lock max_turns
Calendar ↔ Airtable mismatch 7 classes · most urgent → fix the calendar / Airtable by hand
orphan_event mirror_failed cancel_mirror_failed reconcile_conflict reconcile_unresolved verify_unavailable state_unsaved

Filled oxide because these are the only classes where the two systems disagree and the dashboard cannot tell which is right — Google Calendar is the truth, appointments is a mirror.

External system down 5 classes → check system status; transient
llm_unavailable calendar_unavailable lead_unavailable state_unavailable cancel_delete_failed

Dashed oxide — the same signature the widget uses for infra-unavailable, so “something is down” reads the same on both surfaces.

Customer never got the reply 1 class → message them yourself
zernio_send_failed

Its own treatment because the remedy is unique: the answer exists, the customer just never received it.

Budget 2 classes → a spending decision
spend_cap spend_meter_unavailable

Oxide-soft = the widget's guard-trip signature: the system protected itself, nothing is broken.

Operational 4 classes → investigate
normalize_drift dedupe_marker_failed reply_fallback cancel_needs_human
Background jobs 2 classes → reminders / cleanup stopped
reminder_error purge_error

purge_error arrives with a branch value (processed_messages or conversations_pii) — the badge carries it as a suffix when present.

No alert is raised for these — don't wait for one

§4.c: deliberately silent, each for a reason. A dashboard that implied “everything alerts” would be claiming a completeness the system doesn't have.

race_lost kill-switch trip duplicate message 403 unsigned 403 Turnstile widget-lane normalize reject

Reasons: a lost race is a normal outcome of write-then-verify · the owner set the kill-switch themselves · a duplicate was already answered · and alerting on unauthenticated rejects would hand an attacker a denial-of-service primitive.

One more limit, stated once: last_alert_class is a last value, not a history — a newer class overwrites the previous one, and a throttled alert (30 min per class + sender) is never recorded at all. So these badges tell you the latest delivered class per conversation, never the full story of a day.
