1. **HIGH · Main copy — `Record Processed` → `Build Dedupe-Marker Alert`: a failed marker permits a later sequential duplicate booking.**

   **Scenario:** confirmation message M books slot A; appointment and conversation writes succeed, but INSERT into `processed_messages` fails—for example, its INSERT privilege is temporarily denied while SELECT remains available. The customer receives the booking reply and the owner receives an alert. A subsequent legitimate turn establishes a different pending slot B. Redelivering M now passes `Check Processed`, consumes B’s current confirmation state, and creates another event and appointment.

   **Evidence:** `Record Processed` has `"onError": "continueErrorOutput"`. Its error output goes only to `Build Dedupe-Marker Alert`, which emits `dedupe_marker_failed: true`; that branch has no marker retry, booking rollback, or conversation lock. Meanwhile, the event key is:

   ```js
   const bkey = [vi.sender_key, slots.date, slots.time, slots.serviceId].join('|');
   ```

   It contains no message ID. `Write Appointment` conflicts on `gcal_event_id`, so the two different slot keys produce two independent appointment rows.

   A read-only inline Node harness evaluated the committed Code nodes with synthetic inputs. It confirmed: marker failure produces the alert; an absent marker produces `_duplicate: false`; and the **same message ID with two pending slots produces different event IDs**.

   This gap survives after the first execution finishes and can occur within 30 days. The recorded Q5 concurrency exception and expiry bound do not describe it. The alert makes the failure visible but does not prevent the second booking.

2. **Other requested outcomes and bounds**

   | Delivery/state | Reachable outcome |
   |---|---|
   | Sequential replay after a successful marker write, before purge | `duplicate_ignored`; no booking or WhatsApp send. The widget receives the duplicate response. |
   | Concurrent runs reading the same pending booking | Both attempt the same deterministic event ID. On a duplicate-insert response, the second run fetches and verifies the existing event, then continues through slot verification and the appointment upsert. Both can send booking confirmations. |
   | Second run loads state after the first saved `booked` | `Build Event Request` emits an empty event ID; it routes to handoff rather than inserting another booking. |
   | Concurrent runs reading different pending slots | Different event IDs and two bookings are reachable. A run that already passed `Check Processed` never checks it again before booking. |
   | Replay after the marker is purged | It is processed again. An old “yes” can confirm a newer pending slot. |

   **Q5’s actual bound:** for an unchanged booking key and calendar, deterministic event identity, reconcile verification, and the appointment UNIQUE constraint converge on one event identity and one mirror row. They do **not** establish message-level exclusion. Intervening conversation changes can produce different booking keys, and the marker conflict does not suppress either run’s outbound reply. These concurrent outcomes fall within the explicitly unbounded recorded race and are not additional findings.

   **TTL:** Purge selects `created_at < $1::timestamptz` using a cutoff 30 days earlier, then deletes by row ID. Main has no inbound-age check. Thus expiry opens a meaningful replay window, including another booking against later confirmation state. This is outside the stated retention guarantee, so I have not counted the documented 30-day expiry as a finding.
