**HIGH · Owner Actions copy → `Release Handoff Lock`, `Owner Replay Seen?`**

A delayed duplicate can release a **newer handoff without another owner decision**.

Scenario: requests A and B carry the same valid signed body. Both read `handoff` and find no replay marker. A releases the conversation and records its marker. Main subsequently creates a new handoff. B resumes and clears that new lock.

The write checks only identity:

```sql

```

It does not recheck the validated stage, timestamp or replay marker. An offline in-memory SQL probe using the exported statement prefixes produced:

```text
After A, then a NEW Main handoff: ('handoff', 'handoff')
After delayed B, WITHOUT a new owner click: ('new', '')
Release UPDATEs executed: 2; markers: 1
```

This exceeds the accepted B3 bound in `docs/ROADMAP.md:2278`: repeated assignments are harmless only while no intervening state change matters. Main’s `Check Handoff Lock` uses precisely this stage to keep the bot silent during human handling.

**MEDIUM · Owner Actions copy → `Write Verified?`, `Build Release Failure Alert`**

Scenario: the UPDATE commits, then `Re-read Released Conversation` fails or returns no row. `Write Verified?` routes to the shared failure alert, whose exact text includes:
