1. **HIGH · Main copy — `Live Booking?`, `Delete Booking Event`, `Book Reschedule Appointment`, `Delete Old Event (Reschedule)` — dry-run permits real writes.**

   **Scenario:** Set `bot.dryRun=true` while an existing appointment remains booked. Confirming cancellation deletes its real Calendar event. Confirming rescheduling creates a real replacement and can delete the original.

   **Evidence:** The condition `$('Load Config').first().json.config.bot.dryRun === true` guards only ordinary booking. The cancellation and reschedule paths bypass `Live Booking?`. Offline execution with dry-run enabled returned `_cancel_valid=true`, `_confirm_live=true`, and `_reschedule_valid=true`. This exceeds the stated dry-run bound.

2. **HIGH · Main copy — `Book Reschedule Appointment` → `Build Reschedule Insert-Failed State` — a lost response leaves an unaccounted extra event.**

   **Scenario:** Calendar creates the replacement event, but its response is lost or exceeds the timeout. The workflow takes the insert-error branch, keeps the original appointment, and tells the customer the move failed. Both events can remain, while no persisted event reference or alert identifies the possible replacement.

   **Evidence:** The failure builder reconstructs from `const vi = $('Validate Intent').first().json;`, dropping the proposed event’s booking context. `Save State (Post-Write)` persists `$json.gcal_event_id || ''`. Offline execution of the actual builder and alert composer produced an empty event ID, no orphan flag, and only alert class `handoff`; the reply said the original appointment still stands. This concerns an ambiguous successful insert, beyond the recorded cancelled-ID rebooking limitation.

3. **MEDIUM · Main copy — `Get Calendar Busy` → `Compute Availability` — per-calendar failures become availability.**

   **Scenario:** FreeBusy returns HTTP 200 with a calendar-level `errors` array and no busy intervals. The bot treats the failed lookup as an empty calendar and offers the slot without reporting the Calendar failure.

   **Evidence:** `Compute Availability` reads `Object.values(cals)[0] || { busy: [] }` and `firstCal.busy || []`, without checking `firstCal.errors`. An offline fixture containing `errors:[{domain:"global",reason:"internalError"}]` produced `availability.status="available"` and stage `confirming`. The reschedule counterpart correctly threw on the same fixture.
